# Rebuttal

回复的目标：用最短的文字讲清对本文有利的事实，每一句都为真，每一条都尽量回到本文的贡献。

## 流程

1. **先读全材料再写。**
   - 论文源文件：正文、附录、表格。记下节号、附录号、表号，回复里的引用要和 PDF 的编号一致。
   - 每位 reviewer 的全文：summary、strengths、weaknesses、questions、各项分数。strengths 用于写开头。
   - 场地规则：每条评论的字数上限、每位 reviewer 能否发多条、评论对谁可见、能否上传 revision PDF、截止时间。从场地本身查，不凭记忆（查法见 [references/tools.md](references/tools.md)）。
   - 已有草稿和合作者意见：正文、红字、批注，已 resolved 的批注也要看，resolved 不代表正文已经改了。
2. **列待改清单。** 按 reviewer → 条目排列，每条写：位置、谁要求改什么、打算怎么改、事实上的顾虑。几个条目共用的决定（同一件事在几位 reviewer 那里的口径）单独列出，在写到第一个相关条目时先定。
3. **一次讨论一条。** 每条给用户看：完整的拟定文字；每条批注分别怎么处理；需要用户定的点，每点写选项、各自的后果、推荐和理由。用户明确说写入后才改文档。
4. **写入并读回。** 就地修改，每次写完读回核对（做法见 [references/tools.md](references/tools.md)）。
5. **维护两张清单**，写进项目 memory：
   - 已定的口径：例如某个术语怎么解释、某个不一致怎么表述。后面的条目照用，不重议。
   - 对 revised PDF 的承诺：回复里每一句 "the revision adds / describes / cites X" 都要在 LaTeX 里落实，上传 PDF 前逐条核对。
6. **合作者看完修订稿后再准备发帖。**
   - 只取每条的最终回复正文。删掉审稿意见引文、文档自己的结构标题（例如 "Reviewer"、"Draft response" 这类小节名）、文档说明、合作者备注和【旧版】/【新版】标签；回复正文里的加粗条目标签（例如 **W1 & Q1 (…).**）保留。
   - 同一条有两版并存时（例如合作者自己写的整段回复和我们改的那版），问用户发哪一版，不自己判断哪版被取代。
   - 红字不能一律删：合作者用红字写的、要发出去的句子（例如开头感谢句）保留。
   - 转成场地支持的 Markdown：文档里的原生加粗、斜体要转成 Markdown；文档里手打的 `**…**` 已经是 Markdown，不再加一层。
   - 按字数上限拆条，确认每位 reviewer 的回复单独读得懂。
   - 发帖是对外、不可撤回的操作：逐条请用户确认，或由用户自己发。

## 结构

- **开头**：每位 reviewer 一句感谢，点出对方 strengths 里的两项，用两个短名词短语，不展开：
  `We thank Reviewer X for the insightful comments and for highlighting our paper's contributions in **A** and **B**. Below, we provide a detailed response to each concern.`
  各条目开头不再写泛泛的感谢；reviewer 给了具体文献或建议时，可以用一句致谢开始那一条。
- **结论在前**：每条回答的第一句给结论（有致谢句时紧跟在它后面），再给证据、数字、方法细节和置信区间。
- **每位 reviewer 的回复自成一体**：多位 reviewer 共用的结果表，在每位 reviewer 下都放完整一份，因为审稿人通常只读自己那一串。这是对"同一事实只写一处"的有意例外。
- **交叉引用只指向同一位 reviewer 下的条目**（"W1 & Q1 above"、"Q2 below"），不指向别的 reviewer 的回复，也不写 "this rebuttal"。新做的实验写成 "the three runs that we newly trained"。

## 措辞

- **简洁、正面，尽量回到贡献。** 例如：解释为什么不需要某个额外步骤时，说明本文已有的设计让它不必要。
- **默认不说对自己不利的话。** 删掉 "We agree that X is noisy"、"We did not measure"、"we cannot say"、"wastes rollouts"、"The submission omitted" 这类句子，换成同一事实的正面说法，或者不提。例外：合作者亲自写的限定句，推荐删除时说明理由，由用户定。
- **不承认投稿写错，但先查清事实再选写法。** 不写 "the reviewer is right"、"the main text is wrong"、"we correct"。两处描述不一致时：
  - 两处说的是同一个做法、只是详略不同：就这样写，说明简略处的每个说法对应哪个具体做法，再说 revision 把各处统一成同一份精确表述。
  - 两处给出互相矛盾的事实：直接给出正确表述和依据（代码、日志、表格），说 revision 各处统一为这一表述。不写"两处一致"，也不声称错的那处准确。
- **能回答的问题不推给 future work。** 没做的实验，用已有证据给有依据的预期：`Based on these results, we expect ...: ...`。预期的方向由证据决定，依据写在冒号后面。
- **reviewer 建议的做法本文已部分在做时**，先说已有部分在哪（附录号）、做了什么，再回答剩下的差别。
- **"We agree" 要写清楚同意的是什么。** 同意的是 reviewer 提出的要求（例如"发布前必须做筛查、必须有许可"），不是他隐含的前提（例如"你们没做筛查"）。
- **不为了让步而收窄论文的主张**（例如承诺 revision 里不再称之为 generalization）。如果怀疑 reviewer 扩大了某个术语的范围，先查论文里这个术语怎么定义、数据是否全部符合这个范围（不确定就问用户，例如每个任务是否只涉及一个文件），都成立才用一句话澄清本文里这个术语指什么。
- **强调评测的独立性**：结果在第三方基准上测得时写明，例如 `a previously published benchmark whose tasks and references were built independently of our pipeline`。
- **宏观论点要回答 reviewer 实际的担心。** 例如"基准用于模型之间的相对比较"只回答了评测这一侧；reviewer 担心的是训练奖励时，再用数据回答训练这一侧。
- **客观约束要配上现状。** 例如真实数据难拿、没有可发布的许可：先说约束，再说现有方案是可用的最好替代（"to our knowledge, the first open-source ..."，前提是论文里已经这样主张）。
- **同一关切在几位 reviewer 处出现时**，搬用已定的回答，但逐句核对是否和本条的结论冲突（例如"可能不如干净数据训出的模型稳健"放到结论是"影响很小"的条目里会削弱结论，就不搬）。
- **敏感议题**（隐私、许可、伦理）：不承认之前做得不够；描述现在的流程和发布前的保证；新做的步骤用现在完成时陈述，不写它是投稿后才做的，也不用会让人以为投稿前就做过的说法。改完交给负责的合作者看。
- **措辞细节**：主语用 we；术语首次定义后不换（例如 task、test case、output）；同一列表的各项用同一个 `label: description` 格式；删掉和结论无关的细节（工具的默认选项、不支撑结论的大数字）。

## 真实性底线

正面只改措辞和取舍，不改事实。

- **删掉一个限定会让别的句子变假时，保留它**，紧接着给缓解证据（例如：这种情况会被拒，但工具设计让它罕见，审计中出现 0 次）。
- **推断标成预期**："we expect"，写出依据。不写没测过的因果关系。
- **结论的强度不超过证据的范围**：只在两个 checkpoint 上查过的，不写 "never"；小样本审计只支持 "we find no evidence that ..."、"gives no indication that ..."。
- **统计按事实表述，挑对自己有利的那个正确说法**：例如 "the 95% CI of the change rules out an increase of more than 1.8 points"。结论不需要的估计和区间（跨零的，或很宽、显得方差大的）可以不报，改报结论依赖的那个量（例如前后差）；不报不等于可以说显著。
- **核对数字**：检查自洽（例如 912 × 3 = 2,736，报告的是 2,726，就要说明排除的 10 个）；均值、标准差、修正后的估计都重算一遍。
- **措辞不过度断言**：写 "would require additional data construction"，不写 "must be rebuilt as multi-turn demonstrations"。
- **可复核**：引用他人的方法或评测前读原文或代码（例如读官方评测代码，确认它只比较值，才能说本文的评测更严格）；在回复里描述别人的论文前读全文。
- **被直接问到的问题直接答**，即使答案对自己不利（例如问"有几次独立 run"，就写清哪些配置只有一次）。
- **回复对所有 reviewer 可见时**（发帖前确认可见范围）：同一事实各处措辞一致；在一位 reviewer 那里删掉的披露，要保证被直接问到的那位 reviewer 的回复里仍有。
- **合作者建议的说法与事实冲突时**（例如"请以正文为准"，而正文恰恰是不准的那处），指出一次，给推荐，让用户定；用户定了就照做。

## 常见问题的回答顺序

以下顺序来自一篇 RL 数据集与环境的论文。问题类型对得上时参考；每一步只在本文证据支持时使用，证据不支持的那一步删掉，不硬套。

- **训练标签有噪声**：人工审计的结果（判有效、判无效的比例）→ 全量专家审核的成本 → 是否计划出 verified 版本、开放社区贡献（类比 SWE-bench Verified）→ 训练算法是否、如何限制噪声的影响（例如 GRPO 组内归一化：没有 rollout 复现的错误 oracle 不产生梯度）→ 抽查证据 → 独立第三方基准上的结果。
- **评测指标太死板**：说明它清楚、可复现、可验证 → reviewer 举的例子指标是否已经处理 → 对模型输出的人工审计：误拒率及其 RL 前后的变化 → 基准用于相对比较。
- **缺少相关工作**：致谢并说明 revision 补引 → 一句话说明对方做什么 → 本文的不同之处（例如本文训练模型，对方在推理时做 prompting）→ 为什么不作为定量 baseline → 对方方法与本文是否互补。
- **"为什么不先做 X 再做 Y"**：先用结果回答"现有方法是否已经在改善"→ X 的收益取决于什么，指出风险（不是结论）→ 本文的设计是否已经减少了对 X 的需要 → 已发布的环境便于别人测试 X。
- **描述前后不一致**：先判断是详略不同还是事实矛盾，按"措辞"里对应的写法写，附上精确的完整定义。
- **多种子和置信区间**：结论在前（几次 run、区间是否都不含 0）→ 种子控制什么、按固定步数报告、不挑 checkpoint → 区间的分析单位和方法 → 其他数据集上的结果。
- **数据去重 / 泄漏**：做了哪些检查、去掉了多少 → 每类重叠分别怎么覆盖 → 评测集来源与训练集是否不同。
- **泛化 / 基准的代表性**：核实后澄清术语范围 → 基准的来源和人工审计结果 → 真实数据为何难以开源 → 与训练数据的分布差异及在这个基准上的结果 → 主结论是否依赖这个基准。
- **隐私、许可、伦理**：写清楚同意的是哪条要求 → 现有的筛查范围和工具 → 发布前的处理 → 发布方式、许可和维护联系方式（有已发表基准的先例就说明遵循它）。
